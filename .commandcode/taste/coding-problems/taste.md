- When creating coding problem test harnesses, ALL 5 languages (Java, C++, Python, JavaScript, C) must have real test cases — never hardcode "PASS" outputs or leave any language without working test cases. C harness must actually call the user's function and verify results, not just print PASS. Confidence: 0.90
- For C++ harnesses: use `class` instead of `struct` for TreeNode, ListNode, and all other data structures. Confidence: 0.80
- In starter code comments (inside USER_CODE_START section), include the definition of any custom class/struct (e.g., TreeNode with constructor) as a comment — once, not duplicated outside USER_CODE_START. Applies to Java, C++, and C. Confidence: 0.90
- When inserting coding problems into the database, create one separate Python file per problem rather than a single batch script for all problems. Confidence: 0.80
- Use class name "CodeCoder" instead of "Solution" in all test harnesses (Java, C++, Python). Confidence: 0.85
- Include exactly 10 test cases in each harness (5 visible + 5 hidden). Confidence: 0.85
- Do NOT include solution hints or tips in the harness comments — only the problem requirement. Confidence: 0.75
- When inserting a coding problem into the DB, also update remaining.md — decrement the remaining count and remove the problem from the table. Confidence: 0.72
- Deploy coding problem scripts to VM using: python3 compile check → scp → ssh run + cleanup (python3 ... && rm ...; echo '===done'). Confidence: 0.70
- Add problems one at a time, in sequence (increment S.No and follow the order in remaining.md) — do NOT skip problems or batch-add multiple, even if they appear later in the table. Update remaining.md ✓, create and deploy the next Python script, then continue to the following problem. The user has granted full permission to proceed without asking — "dont ask for permission full permission" — so do not pause to ask "next?" after each problem; just keep going autonomously. Confidence: 0.90
- Write coding problem descriptions in English with proper line-by-line or bullet-point example explanations. Confidence: 0.70
- User refers to problems by their sheet number (e.g., "q28 add kar" = add problem #28) and explicitly requests any skipped problem (e.g., "next" led to q29, then user followed up with "q28 add kar") — they track the sheet and expect every problem in the list to get added eventually. Confidence: 0.60
- After deploying a coding problem to the DB, update its status in Have_To_Add.md sheet from ❌ to ✅. Confidence: 0.80
- Harness output must follow the format `TC:<n>:PASS` (visible) / `TC:<n>:FAIL:hidden` (hidden); hidden tests never leak input/expected/got, and every test() call is wrapped in try-catch so one crash doesn't kill the remaining tests. Confidence: 0.85
- Before inserting problems from a sheet, query the DB for existing problem titles and skip/avoid duplicates (e.g., match case-insensitively, handle title differences like "GCD of Two Numbers (Euclidean Algorithm)" vs "GCD of Two Numbers"). Confidence: 0.70
- After inserting problems, restart the backend (`sudo systemctl restart codecombat`) to clear cache and verify the insert via psql (SELECT count / list problems and code_snippets). Confidence: 0.70
- When a harness-standard violation is discovered (e.g., C++ `struct` instead of `class`, C harness not calling the user function), go back and fix already-deployed problems in the DB — not just apply the fix to future problems. Confidence: 0.65
